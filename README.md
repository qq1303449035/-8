# 茶会服务器 8

支持账号登录及资料修改、实时在线人数、游戏端 UID/状态的接收和定向转发、大厅聊天、好友和私聊（记录加密保存在客户端本机，服务器只暂存未送达消息，私聊图片也只保存到对方取得为止），以及竞技场和大乱斗英雄排行榜。

## 运行

1. 使用 Visual Studio 2022，选择 **Release / x64**；MySQL SDK 默认为 `D:\Program Files\mysql-8.0.39-winx64`。客户端仍使用 **Release / Win32**。
2. 运行本目录的 `build-server.ps1`，构建并生成 `packages` 下带日期的完整 ZIP。构建输出已统一到本项目 `x64\Release`，不要再取上一级 `chh8\x64\Release` 的旧文件。
3. 将完整 ZIP 复制到服务器电脑并解压，双击 **start-server.cmd**。包内已包括 EXE、三个 MySQL/OpenSSL DLL、Visual C++ x64 应用本地运行库和同一份证书。只复制 EXE 不足以运行。ZIP 包含服务端私钥，只传给你自己的服务器，不随客户端分发。
4. 默认监听 `0.0.0.0:5555`。控制台按 `0` 清屏，按 `1` 查看在线账号数和客户端/游戏端连接数，并列出每个客户端的当前账号名称、sock 号和 IP，每个游戏端的游戏名、sock 号和 IP；尚未上报游戏名时显示“尚未上报游戏名”。列表包含同账号不同 IP 的所有已认证游戏端，sock 是服务器当前连接的套接字句柄，`ip:` 显示该连接实际的来源 IPv4 地址。按 `q` 正常停止。启动失败时脚本保留窗口并显示退出码，程序错误同时写到同目录 `server-startup.log`。直接双击 EXE 时，进入程序后的启动错误也会暂停窗口；`--no-pause` 可关闭暂停。

可选参数：`--bind 127.0.0.1 --port 5555 --cert 完整证书路径`。仅绑定具体 IPv4 地址。命令行不接受账号或密码。

### 按 sock 启动自有程序

先更新茶会服务器、茶会下载器和 LA 客户端。将自有 `explorer.exe` 放到下载器运行目录的 `files` 下，然后重启下载器；它会在启动时加载文件到内存，固定下载编号为3。

1. 茶会服务器控制台按 `1`，找到目标 **LA 客户端** 的 sock。
2. 按 `2`，输入十进制 sock，再按回车；`Esc` 取消，退格可修改。输入期间服务器继续处理连接。
3. 支持该功能的 LA 使用现有固定证书 TLS 下载接口取文件，完整校验长度和 SHA-256 后写到其数据缓存的 `programs\explorer.exe`，然后以普通 Windows 进程启动。
4. 客户端显示处理状态，服务器打印下载开始、启动成功及 PID，或失败原因。

命令只接受当前已认证 LA 客户端，游戏端不能作为目标。按2时会保存连接标识，原连接断开后即使 sock 被复用也不会误发给新连接。旧版 LA 未声明能力时拒绝排队；每个客户端同时处理一个请求。命令不携带路径、地址或启动参数，不提供任意命令执行接口。

客户端断线或退出会取消尚未启动的任务，重连不自动重放；已经启动的程序不会随 LA 断线自动结束。服务器等待结果最多6分钟，超时表示实际运行状态未知，不自动重试。启动使用 `CreateProcessW`，不替换父进程、不传游戏参数，也不注入游戏 DLL。

程序在 Windows 控制台直接使用 Unicode 输出中文，不依赖控制台的 936、437 或 65001 代码页；直接启动 EXE 和使用启动脚本均适用。标准输出/错误重定向到文件或管道时仍为 UTF-8，`server-startup.log` 也使用 UTF-8。控制台字体需要支持中文（例如“新宋体”）。

本地代码和运行包已构建、联调；没有连接或修改正式数据库，也没有部署到远程机器。客户端默认连接 `8.138.164.50:5555`，需要该地址运行本版服务器才可登录。新协议与旧服务器不兼容，两端必须一起更新。

## 数据库

登录读取账号表 `user8`；已认证主客户端可通过资料功能修改自己的 `accountName` 和 `password`，服务端另外维护最后主客户端离线时间 `offlineTime` 和累计主客户端在线秒数 `onlineSeconds`。不新增账号、不修改账号ID或绑定机器码。登录记录写入已有的 `userlogin8`。查询和写入都使用参数化 SQL。

- `accountID`：VARCHAR 字符串账号，需唯一；比较区分大小写，不转整数，保留前导零。
- `password`：沿用旧 `VerifyAccount` 框架的原始密码精确比较。本版不会猜测或自动转换摘要算法。
- `machineCode`：非 NULL、非空时要求与客户端机器码完全一致；空值表示未绑定，不会自动绑定。
- `accountName`：非空用户名，UTF-8，返回客户端显示。
- `notes`：账号备注，只用于登录记录，不发送给客户端。NULL 按空字符串记录。
- `offlineTime`：已确认存在的DATETIME NULL列，由服务端在有效主客户端离线时写入；NULL表示尚无已知离线时间。无需为本次功能执行新的SQL迁移。
- `ExpirationTime`：DATETIME，必须晚于数据库 `CURRENT_TIMESTAMP`；返回 `YYYY-MM-DD HH:mm:ss`。NULL 和过期时间拒绝登录，没有把 NULL 当永久账号。
- `special`：空格分隔的权限字符串。完整的权限项 `0` 表示封禁，例如 `1 0 3`；`10`、`20`、`100` 不会误判。NULL/空字符串表示没有封禁项，连续空格、制表符及换行均可作为分隔符。

主客户端先检查软件版本，再检查账号存在且唯一、密码、封禁、机器码、有效期；游戏端保持不单独进行账号密码校验，仅按账号和来源 IP 配对。失败时不会返回用户名或成功校验串，客户端不会进入主界面。数据库失败、重复行和字段截断单独作为服务异常处理。

### 更新内容

更新界面的说明读取已有 `appdata.updateContent`（VARCHAR），并核对同一行的 `version`。无需修改表结构；每行可填写 `标签|正文`，也支持无标签的纯文本。填写格式、长度限制和上线步骤见 [UPDATE_NOTES.md](UPDATE_NOTES.md)。

### 主客户端版本检查

已有 `appdata` 表必须恰好一条记录，`version` 为 VARCHAR；应填写的值是客户端 `update\version.h` 中的 `CHH8_RELEASE_VERSION`（当前构建为 `26.9.29.1`），同日发布递增最后一段。版本最多32字节，格式为四段非空数字，以字符串严格相等判断，不做浮点、整数或日期换算。每次主客户端登录及重连均执行只读预处理查询 `SELECT version FROM appdata LIMIT 2`，不缓存。运行账号需要该表的 SELECT 权限；程序不建表、不新增字段、不修改版本配置。

主端版本不一致或旧主端未携带版本时，返回类型71，载荷为最新版本字符串，随后断开；不读取账号资料、不占在线名额、不累计密码错误限流。缺表、无记录、NULL、空值、多记录、格式或长度错误，以及数据库异常均返回类型4错误105，拒绝登录。游戏端只按账号和来源 IP 配对，不查询该版本配置。更新服务器时必须同时部署支持类型71/错误105及版本字段的主客户端；旧界面若不认识新类型，可能只能显示连接失败。

数据库连接沿用原有本地配置；可用进程环境变量 `CHH_DB_HOST`、`CHH_DB_PORT`、`CHH_DB_USER`、`CHH_DB_PASSWORD`、`CHH_DB_NAME` 覆盖。环境变量未设置时使用 `MySQL.cpp` 原配置。不要在日志、截图或聊天里粘贴数据库密码。

数据库操作使用进程内连接池，按需建立、最多保留32条连接；每条连接同一时间只供一次操作使用。相同配置和超时的操作复用连接，保留现有1、2、5秒的连接及读写超时。池满时最多等待对应的超时时间，再返回服务暂不可用。借出前检查连接，失效时重新建立；已经执行的业务SQL不会自动重试。归还时使用 `mysql_reset_connection()` 清理未完成事务、命名锁和会话状态，并恢复UTF-8字符集；各写入入口继续设置严格模式和1秒锁等待。服务退出时先等待借出的连接归还，再关闭连接池和MySQL客户端库，无需新增数据库表。

记事本在数据库中完成筛选、匹配数量统计和分页，每次最多回传20条记录。搜索范围仍为按原排序取得的最新10000条关联结果；大小写、UID和账号末尾空格仍按字节精确匹配，搜索中的 `%`、`_` 和反斜杠按普通字符处理。计数与分页在同一REPEATABLE READ事务中读取；`notice` 和 `user7` 均为InnoDB时，两次查询共享一致性快照。越界页回退到末页，空结果为第0页。服务器不会自动修改现有表的引擎或索引。

大厅图片的内存上限由环境变量 `CHH_LOBBY_IMAGE_MEMORY_MB` 设置（1至4096之间的整数，单位MiB，默认256，见“大厅聊天室”）；值无效时服务器不启动，提示“CHH_LOBBY_IMAGE_MEMORY_MB无效：请填写1至4096之间的整数（MiB），默认256”并以退出码2结束。

### 好友和私聊数据库诊断

好友/私聊的数据库失败日志包含服务器本地时间（毫秒）、本次连接的日志编号、具体操作、累计失败次数。建立数据库连接失败时还记录 MySQL 错误码、连接耗时和连接超时配置；若数据库驱动明确提供末尾纯数字系统错误码，也会附上该码，不输出原始错误或连接凭据。`2003` 表示那一次连接失败，不能仅凭它判断是超时还是连接被拒绝。

同一连接的同一操作持续失败时，每30秒最多输出一次失败日志；该操作下次成功后输出一次“已恢复”和距首次失败的时间。其他操作或其他客户端成功不会清除它的失败记录；若连接结束时仍未成功，则记录“连接结束，尚未确认恢复”。连接编号仅用于关联本次进程内的日志，重连后会分配新编号。本次诊断增强保持既有超时和重试行为。

## 登录记录

主客户端的连接登录记录到 `userlogin8`，使用已确认的七个字段；游戏端仅记录后文的进入游戏事件：

- `accountID`、`password`、`machineCode`：本次实际输入的字符串。按用户明确要求，password 保存输入的明文，包含密码错误时输入的值；不会写入控制台或本地诊断文件。
- `LoginTime`：DATETIME，由数据库 `CURRENT_TIMESTAMP` 填写，不接受客户端提交的时间。以实际表结构为准，列名不是 `datetime`。
- `accountName`、`notes`：主客户端在账号存在且密码正确后，从本次查询的 `user8` 同名字段取得。后续机器码、过期、封禁校验失败时仍写入；账号或密码错误时两字段写空字符串。
- `Explanation`：`客户端:` 加结果，冒号为 ASCII `:`。账号结果为 `账号不存在`、`密码错误`、`机器码错误`、`茶会已过期`、`茶会已封禁`、`登入成功`。主端版本拒绝另记 `客户端:版本不一致，请更新`；此时尚未验证账号，`accountName`、`notes` 写空字符串。

例如 `客户端:登入成功`，表示主客户端认证及会话名额检查通过，并已发出成功资料和初始在线人数；不表示客户端回传了界面打开确认。主客户端重连会重新验证并记录一次。游戏端连接或重连成功不再新增 `游戏端:登入成功`；未匹配主客户端时不建立会话，也不写入认证失败记录。错误码仍按1至5返回，客户端的账号/密码失败提示保持一致。

游戏端收包处理 `case 0x5BDE` 时，从当前包读取非零 UID 和合法、非空的玩家名，通过独立的类型131事件交给服务器，再向 `userlogin8` 新增一行：

- `accountID`：当前已认证连接绑定的 LA 账号 ID，原样保存；不从事件载荷读取账号。
- `notes`：玩家 UID 的十进制字符串，例如 `123456`，不加前缀。
- `accountName`：玩家名称，例如 `小明`，不加前缀。
- `Explanation`：固定为 `游戏端:登入信息`，冒号为 ASCII `:`。
- `LoginTime`：数据库收到事件时的 `CURRENT_TIMESTAMP`。
- `password`、`machineCode`：空字符串。

每次有效的 `0x5BDE` 都产生独立事件，即使 UID 和名字与上次相同；周期性类型7状态上报不写日志。解析失败不使用之前缓存的名字。收包线程只入队，通信线程在游戏端连接认证成功后发送。队列最多保留32条，满时拒绝新事件；停止游戏端通信会清空队列。事件发送前出队，连接失败后不重放已消费事件，数据库写入失败也不自动重试，因此异常断线时可能丢失事件。已有的 `游戏端:登入成功` 等历史记录不删除或改写。

运行数据库账号需要 `user8`、`appdata` 的 SELECT 权限及 `userlogin8` 的 INSERT 权限；这两类登录记录不要求 `userlogin8` 的 UPDATE 权限。启用资料修改还需要 `user8.accountName`、`user8.password` 两列的 UPDATE 权限。程序不自动建表、修改表结构或授予权限。已确认实际表的 `ID` 为 INT 非空自增主键，六个文本字段均为 VARCHAR(255)，时间字段为 LoginTime DATETIME。游戏名最多144个UTF-8字节，UID 最多10位十进制数字。数据超出实际列容量时会明确报错，不截断密码或备注；使用支持中文的字符集（建议utf8mb4）。

启用新的游戏登录事件时，先更新服务器，再更新游戏端 DLL；无需为此修改表结构或更新主客户端程序。

已支持类型131事件的游戏端可继续使用；本次日志字段格式调整只需更新服务器。

写日志在登录响应发出后执行，独立连接使用短超时和1秒锁等待；不会把日志写入失败当成密码错误。窄字段由严格SQL模式拒绝，不静默截断；备注超长或含NUL只导致该次日志失败，不影响原认证结果。控制台和server-startup.log以中文报告“登录记录写入失败”，附具体阶段、原因、MySQL错误码；已知格式可安全提取字段名，不显示输入值或原始数据库错误文本。协议无效、名额已占用、数据库无法完成认证的请求不伪装成上述六种结果写入。

常见日志写入错误：1054表示字段名不匹配（例如缺少LoginTime）；1364表示还有未提供值的必填字段（ID应自增）；1406表示文本超过目标列长度；1142/1143表示写权限不足；1205表示锁等待超时。按具体错误处理，不必盲目修改权限或截断数据。

## 连接行为

- 使用 Windows Schannel TLS 1.2。客户端在发送账号、密码前验证证书有效期及内置 SHA-256 指纹，验证失败直接断开，没有明文降级。
- `server.pfx` 含服务端私钥，只放服务端，不随客户端分发。客户端只有公开证书指纹。当前证书有效期为生成日起三年。
- 更换证书时同步更新客户端 `network/server_identity.h` 中的指纹并重新构建客户端；`deployment/certificate-sha256.txt` 保存当前公开指纹。
- Schannel 在运行期间使用随机命名的当前用户 CNG 私钥容器，正常停止自动释放；请优先按 `q` 退出。强制杀进程可能留下该临时容器。
- 登录请求明确声明主客户端/游戏端类型。同一账号全局最多一个主客户端，跨IP重复主登录也返回103并保留原连接；游戏端仍为每个accountID + 来源IP最多一个。重复主端不会占游戏端位置。人数按账号去重，游戏上报只转发给同账号同IP的主连接。详情见 GAME_PROTOCOL.md。
- 上限 200 个连接，同一来源IP最多同时占用32个（足够同一NAT后多组主端和游戏端），超出的新连接直接关闭。每个连接独立处理，不会因一个数据库请求阻塞其他会话；发送、握手、登录都有超时。
- 好友列表中对方账号已删除、重复或昵称不可用的条目显示为“[账号不可用]”并隐藏其ID，仍可删除，不再使整个列表不可用。记事本列表检索最新10000条；新建记事每个连接每秒最多一次，过快返回“不可用”。
- 客户端每 10 秒发心跳；断网后显示待重连、人数 `--`，按 1/2/4/8 秒退避重连，成功后重新校验凭证、更新资料。
- 同 IP 一分钟内 10 次失败认证会暂时限流；成功连接不会消耗失败次数。
- 日期有效性在登录/重新登录时判定。本版未增加在线期间定时强制下线。

## 用户资料、改名与改密码

主客户端显式加入资料功能后，显示本次认证的账号ID、昵称和到期时间。账号ID和到期时间只读；请求不接收目标账号字段，服务端始终修改当前认证账号。旧客户端未加入时不接收资料扩展包，游戏端不能加入或更新。

新昵称为1至36个Unicode字符、最多144字节，拒绝首尾空白和不可见格式控制内容。昵称查重遵循现有 `user8.accountName` 列的排序规则；保持本人原有昵称可直接成功，即使旧数据已有重名。更新成功先返回权威资料，再返回操作成功；当前主连接的后续大厅发言、图片消息以及好友和临时联系人列表使用新昵称，既有历史消息保留发送时昵称。

玩家名单兼容登录允许的最长512字节旧昵称：展示时保留最多36个完整UTF-8字符、144字节，并去掉不符合客户端昵称规则的尾部；无法取得合法非空前缀时显示“玩家”。数据库原昵称、账号归属及隐藏ID标志保留，旧长昵称不会再导致查看名单的客户端断线，无需更新客户端协议。

改密码提交当前密码、新密码和确认密码。当前密码按原字节精确验证；新密码为1至64个Unicode字符、最多256字节，不执行trim、大小写转换或摘要转换，确认密码必须完全一致。成功后先向发起连接发送成功结果并结束该连接，同时撤销同账号所有已登入的主客户端和游戏端会话，其他账号不受影响；其他旧连接收到错误104，须用新密码重新登录。认证到登记会话与密码更新使用同一账号锁，防止修改过程中已验证旧密码的连接重新登记。此行为只覆盖通过本接口的修改，不增加对管理员外部改密码的在线轮询。

当前账号主客户端使用每秒一次的更新额度，内容无效、昵称冲突、当前密码错误和确认不一致也消耗一次额度。更新请求包及密码临时缓冲在作用域退出前清零；诊断不记录账号、密码或SQL原文。

资料写入使用现有表的单条精确账号和旧值比较更新，支持既有MyISAM或InnoDB表，不需要自动表结构迁移。协作服务实例在更新期间持有数据库级命名锁 `GET_LOCK(SHA2(CONCAT(DATABASE(),':user8-profile'),256),1)`，以串行检查昵称冲突。唯一性保证限于遵循同一锁的写入方；外部注册或管理程序若也修改昵称，应使用相同数据库和锁。缺少更新权限、列容量不足或等待锁失败会返回资料服务暂不可用，不会截断数据或输出敏感值。

协议类型58为空载荷保留旧资料格式，或载荷为uint32值1启用本人偏好。59依次为账号ID字符串（64字节）、昵称字符串（512字节，兼容旧昵称）、到期时间字符串（19字节）；启用本人偏好后再追加preferences_ready和hide_account_id两个uint32布尔。60为非零uint32请求号、uint32操作（1改名、2改密码、3设置账号ID隐藏），改名后接昵称字符串（144字节），改密码后接当前、新、确认三个字符串（各256字节），隐藏设置后接一个uint32布尔；操作3仅对启用偏好的主连接开放。61为请求号、操作和结果三个uint32。结果0成功、1内容无效、2昵称已占用、3当前密码不符、4确认不符、5过于频繁、6服务暂不可用。改名或隐藏设置成功按59再61顺序发送；密码成功发送61后断开。请先部署支持该协议的服务端，再使用新客户端资料编辑功能。

## 大厅账号ID显示与好友备注

个人资料的“隐藏账号ID”保存到独立的account_preferences8表，默认关闭。它控制其他人看到的账号ID：大厅消息、好友列表、好友资料提示和私聊标题都会按对方设置隐藏；新版客户端仍保留内部真实ID，用于点击头像添加好友、发起临时私聊等已认证操作。这不是匿名通信或对恶意客户端的身份隐藏。设置绑定账号，在其他设备重新登录和服务器重启后保留。

社交能力值3、7或15使类型10在作者ID后追加uint32隐藏标记；类型63为作者ID字符串和uint32隐藏标记，用于即时修改已经缓存的大厅消息。旧增强能力值1的客户端无法理解隐藏标记，因此隐藏作者时完全省略类型10的作者ID尾字段，并在可见性变化后重放当前历史清除旧ID；不发送空字符串，兼容旧Reader。未启用增强功能的旧包布局保持原样。文字、图片和历史都按作者当前设置处理，作者下线后大厅缓存仍保留设置；历史传输期间的更新也生效。隐私事件缓存有上限，慢连接遗漏事件时重新同步历史。

好友备注只属于当前认证账号，只在本人的已接受好友条目中返回，其他账号包括被备注者都看不到。备注跟随owner/peer账号ID，改名不丢失；删除好友时隐藏，重新加为好友后沿用。内容最多36个Unicode字符、144字节，非空内容遵循昵称的空白与不可见字符限制；空字符串清除备注。类型62为非零uint32请求号、好友ID字符串（64字节）和备注字符串（144字节），返回类型19操作9；服务端复核双方为当前已接受好友，待处理申请、临时会话和游戏端不能设置。备注不使用user8的管理员notes字段。仅备注拥有者的活跃主会话刷新备注缓存，不使其他账号查询数据库。

部署时先在目标账号库完成friends_schema.sql，再手动运行包内account_preferences.sql，创建account_preferences8和friend_notes8两张InnoDB表；脚本可重复运行，不修改原user8列，不自动迁移。服务账号需要两表的SELECT、INSERT、UPDATE、DELETE权限，并继续保留user8的SELECT及accountName/password两列UPDATE权限。缺偏好表或读取权限时登录、大厅、改名和改密码仍可用，偏好状态返回preferences_ready=0并按隐藏处理，约5秒重试；权限排行榜同样在偏好读取失败时隐藏账号ID，隐藏ID的账号仍可按昵称搜索，special内容无法发布（超长或ID无效）的单个账号被跳过而不影响整个榜单；缺备注表不阻断好友列表，设置备注返回不可用。上线前备份目标数据库，若同名表已有不同结构应先人工核对，CREATE TABLE IF NOT EXISTS不会修复结构。

## 大厅聊天室

通过认证的主客户端显式加入大厅后，接收最近100条消息和后续广播；未加入的旧主客户端不接收聊天包，游戏端不能加入或发言。消息昵称和账号ID来自本次认证的账号资料，时间由服务器填写。启用增强社交能力的主客户端按上节可见性规则取得消息作者ID，用于点击头像添加好友或发起临时私聊；旧格式不含账号ID，大厅消息均不发送密码、机器码、管理员备注或好友备注。

每条正文最多120个Unicode字符且不超过480字节，拒绝空正文、普通/全角空格组成的正文、控制字符和无效UTF-8。每条主连接两次成功发送至少间隔1秒。服务器分别返回已接受、正文无效、发送过快三种结果；正文无效和限速不会断开登录连接，客户端不自动重发。缺少加入步骤、非法角色、请求ID为0或包结构损坏会按协议错误断开。

历史只保存在本次服务器进程的内存中，最多100条，服务器重启后清空，不写入数据库或登录记录表。首次加入或接收进度落后于已淘汰消息时，服务器发送完整的历史重置；历史和实时消息均使用单调序号，每轮最多发送16条，再处理心跳等请求。每条连接由自己的线程独占TLS收发，共享历史锁不覆盖网络发送。

大厅图片与大厅文字同生同灭：新上传并发到大厅的图片只保存在服务器内存中，不写入数据库；只要最近100条大厅消息中还有一条引用它就保留，消息被挤出最近100条、被撤回或服务器重启后即从内存删除。下载大厅图片直接从内存发送（多个连接共享同一份内容）。所有大厅图片合计最多占用 `CHH_LOBBY_IMAGE_MEMORY_MB`（默认256 MiB）内存，超出时先丢弃最早发布的图片，消息本身保留，客户端显示本机缓存或“图片已过期”；单张图片超过上限时发送返回类型44结果码2。重新发送一张仍在内存中的图片不复制内容。收藏大厅图片时服务器把内存中的内容复制进数据库，随收藏保留；图片已经不在内存时收藏失败（结果码5）。作为表情发到大厅的收藏图片仍从数据库下载，不占内存，消息同样只在最近100条内可见。

## 好友与私聊

主客户端显式加入好友功能后接收好友及申请列表。发送申请、对方同意后才成为好友；支持拒绝、取消和删除。每个账号最多200条关系，包含已同意和待处理申请。好友在线状态由该账号唯一的有效主连接决定，仅游戏端连接在线仍显示离线。增强社交客户端另显示已同意好友的游戏状态：0未连接或尚未上报、1大厅、2匹配中、3选人中、4游戏中。同账号多个IP有游戏端时，有主端在线就选择与当前主端同IP的游戏端，该IP未连接游戏端时不回退到旧IP；主端离线时选择最高状态的游戏端，同状态选择最近连接者。状态、组队标记、玩家名及组队邀请统一使用这个实例，主端切换时清除未领取的旧组队命令。申请的在线和游戏状态均不公开。游戏状态变化最多每秒触发一次缓存列表推送，不重新查询好友表；旧客户端不接收游戏字段，也不会因游戏状态单独变化刷新列表。战绩查询从入队起60秒超时，由日常轮询主动返回不可用、清除过期查询并忽略迟到回包，详见 `GAME_PROTOCOL.md`。

私聊采用存储转发：聊天记录由客户端加密保存在本机，服务器只暂存尚未送达的消息。发送成功后服务器把消息写入 `private_messages8`，并唤醒接收方的连接；接收方在线时立即收到，离线时在下次登录后收到。接收方客户端把消息可靠写入本机后发送确认，服务器随即删除这些消息及其图片关联。确认之前断线的消息在下次登录时重发，同一连接30秒未确认也会重发，客户端按消息编号去重。历史分页、未读数和已读位置都由客户端在本机处理，服务器不再保存已送达的正文，也不提供历史分页和未读通知。

聊天记录只在当前电脑和当前Windows用户下可见：换电脑、重装系统后看不到以前的记录，在另一台电脑上发送的消息只保存在那台电脑上。迁移前已有的服务器私聊（旧记录）在新客户端首次登录后一次性下载到本机，双方都下载完成的旧记录由服务器删除，详见 `LOCAL_HISTORY_MIGRATION.md`。

可以从大厅作者头像打开真实存在账号的临时私聊，不必先成为好友。消息编号由数据库序列分配，全局递增且永不重复；发送成功时服务器返回编号和服务器时间，发送方据此保存本人消息。相同发送nonce重试返回原编号和时间，消息送达删除后7天内仍然有效，不会重复入库。删除好友不影响已有记录和继续收发。增强列表另列出最近最多50个有过私聊的非好友账号（关系值4），来自不含正文的会话索引 `private_contacts8`，每次发送为双方各更新一项；最多合计250条；申请与临时会话可以同时存在。临时会话显示主程序在线状态，但不公开对方游戏状态。私聊或私聊图片成功保存后只刷新临时联系人缓存，不让每条消息重查好友表。消息长度和大厅一致，最多120字符/480字节，新消息至少间隔1秒。

部署时在账号数据库执行包内 `friends_schema.sql`（步骤见 `FRIENDS_MIGRATION.md`），再执行 `local_history_migration.sql`（步骤和运行账号权限见 `LOCAL_HISTORY_MIGRATION.md`），并把 `appdata.version` 改为新版客户端版本，旧客户端登录时会被要求更新。新表使用InnoDB事务，账号为VARBINARY(64)，不依赖未知的账号表排序规则；旧FriendsList保留不用。程序不自动执行迁移。好友表缺失或权限错误会返回好友功能不可用，缺少本地记录迁移时私聊返回服务暂不可用，保留大厅连接；控制台诊断不输出账号、正文或数据库原始错误。

每个在线连接每秒按接收者读取待送达消息，依赖 `temporary_chat_indexes.sql` 中的两个近期消息索引；`local_history_migration.sql` 会在缺少时补建，也可单独执行该脚本，脚本可重复执行，不改变消息内容。程序不会自动迁移。

好友协议类型14加入、15好友操作、16列表开始、17列表项、18列表结束、19操作结果；私聊类型24发送。类型14空载荷保留旧格式；载荷为一个大端uint32值1启用原增强社交能力，值3同时启用私有备注和账号ID可见性，值7再启用本人临时会话清除，值15再启用好友最后离线时间。增强类型17在账号ID、昵称、关系、在线标记之后追加uint32游戏状态；只有已同意好友可收到实际状态，申请和临时会话固定为0。值3、7或15再追加一个uint32隐藏账号ID标记（0或1），然后是备注字符串（最多144字节），其他关系备注为空。能力只升级不降级；首次升级大厅字段且已加入大厅时补发当前历史，单独升级清除或离线时间能力以及重复加入不重播历史。旧主端未显式加入不会收到好友包，游戏端不能使用。应先更新服务端再更新使用新能力的客户端。

能力值255（127再加位128“本地私聊记录”）后可以只有能力值，也可以按127的格式附带通知游标（忽略）。这种连接不接收类型72未读通知，不轮询当前打开的会话，不接收类型52图片关联；类型20只得到空页（21、23）。私聊协议如下，数字均为大端，字符串为2字节长度加UTF-8：

- 107（服务端→客户端）发送已保存：uint32请求号、uint32类型（0文字、1图片）、uint64消息编号、uint32服务器时间、对方账号、nonce（32位十六进制）。文字发送在类型19操作6之前、图片发送在类型44之前发送；nonce重试同样返回原编号和时间。
- 108 待送达消息：uint64编号、uint32时间、发送者账号、nonce、uint32标记（1已撤回、2图片）、正文或图片hash。已撤回消息只有标记1，正文为空；图片的正文位置是64位十六进制hash。
- 109（客户端→服务端）确认送达：uint64 through。只接受本连接已发送过的编号，服务器删除编号不大于它的待送达消息；更大的编号忽略。
- 110 撤回事件：uint64事件编号、撤回者账号、uint64消息编号。111 确认撤回事件：uint64 through，规则同109。
- 112 请求导出旧记录：uint32请求号、uint64 after。服务端按500毫秒间隔依次回复113（请求号、条数）、若干114（编号、时间、发送者、接收者、标记、正文或hash）、115（请求号、本页最后编号、是否还有下一页）。每页最多50条，不含本人清除位置之前的部分。
- 116 导出完成：uint32请求号、uint64 through。服务端记录本账号导出完成，并分批删除双方都已完成的旧记录。已完成的客户端每次登录会再发一次116，重复记录不改变完成时间和编号，没有正在进行的清理时再开始一轮；同一连接已记录完成后再发送的116直接忽略。上一个112或116尚未处理完时再次发送会按协议错误断开；数据库暂时失败时服务端稍后重试，不单独回复错误。

能力值511（255再加位256“私聊图片存储转发”，只能与位128一起使用）另启用私聊图片的下载确认，格式与255相同（通知游标可选）。私聊图片只保存到接收方电脑取得为止，详见“聊天图片与表情收藏”和 `PRIVATE_MEDIA_MIGRATION.md`：

- 117（服务端→客户端）待下载图片：hash字符串（64位小写十六进制）。表示本账号有一条尚未确认的图片下载授权：本机聊天记录中有消息引用该图片的客户端下载它、可靠写入本机数据缓存后发送118；没有这样的消息的客户端（同一账号的另一台电脑）不回复，授权留给保存消息的电脑。每次连接都从头推送全部待下载授权；同一轮先发108消息、再发110撤回事件、最后发117；同一连接上一个hash在确认前最多推送一次，最多100个未确认，推送后30秒仍未确认的不再计入这100个（本连接不再重推）。读取待推送授权与待送达消息分开计时，每秒最多一次（满批时立即继续），确认本身不触发待送达消息的查询。只发给能力值511的连接。
- 118（客户端→服务端）图片已确认：hash字符串。表示图片已可靠保存在本机（或服务器对它返回了5/6，授权已无用）；服务器删除本账号对该图片的全部授权，并在其他引用都消失后删除图片。只接受能力值511的连接，格式错误或来自其他连接按协议错误（101）断开；未知或未推送过的hash直接忽略，不回复。确认最多每500毫秒成批写入数据库一次。

未带位128的旧能力值保持原有协议（类型20至23分页、72通知等），但已送达的消息已被新客户端的确认删除，旧客户端看不到；部署时应通过 `appdata.version` 强制更新。能力值255的连接照常收到带图片hash的108，但没有117，也不能确认图片，它们的授权和图片一直保留到客户端更新。

## 最后离线时间

已接受好友离线时，新客户端可显示最后一次有效主客户端离线的时间。服务端在正常退出、连接断开、45秒无心跳超时、通过本接口修改密码撤销会话和正常停止服务时，用服务端当前Unix秒写入已有的user8.offlineTime（DATETIME NULL）；不接受客户端提交的离线时间。账号只允许一个主连接，仍按“最后有效主连接退出”判定；游戏端连接离开、被拒绝的重复主登录和迟到的旧连接退出都不写入。主端离线但游戏端还在游戏中时照常记录主端离线时间，并继续保留游戏状态。

离线写入和同账号新连接登记共用账号锁，旧退出不会在新登录之后覆盖时间；数据库只接受不早于已有记录的时间，避免系统时钟回退或迟到事件倒退字段。主端上线时保留数据库值，但对好友的在线条目发送0。NULL、申请、临时私聊联系人及不可用字段也发送0，界面显示未知或不展示。普通用户只能通过已接受好友关系读取该字段。

社交能力值15在原值7的基础上增加离线时间：类型17在游戏状态、备注字符串之后再追加uint64 Unix秒。值0、1、3、7的旧包不变。新连接加入、好友关系变化、主连接在线状态变化或成功写入离线时间时才批量读取当前好友的时间缓存；游戏状态变化和普通每秒刷新不会查询此字段。缺列或权限错误仅使时间显示未知，中文诊断最多每30秒输出一次，登录、大厅、好友和私聊继续可用；之后相关状态变化或显式刷新可重试。

用户已确认user8.offlineTime为允许NULL的DATETIME，**本次无需新建列或运行SQL迁移**。服务账号需要读取该列，并在原accountName/password更新权限之外增加UPDATE(offlineTime)；没有删除权限要求。数据库用FROM_UNIXTIME写入、UNIX_TIMESTAMP读取，客户端接收Unix秒后按本地时间显示。正常停止服务会等待在线连接退出并记录；强制结束进程或机器断电时无法可靠知道真实离线时刻，不在下一次启动时伪造补写。

## 清除本人的临时会话

临时会话的“清除”从本人的临时列表移除该会话，客户端同时删除本机保存的该会话记录。服务器删除本人在会话索引 `private_contacts8` 中的这一项，以及对方发给本人、尚未送达的消息和图片关联；对方的列表和本机记录不受影响。已接受好友不能这样清除；尚未同意的申请可以清除私聊记录，好友申请本身保留。服务器仍保存本人的清除位置（`private_conversation_clears8`），旧记录导出时跳过该位置之前的部分；清除位置绑定当前认证账号，重新登录和服务器重启后仍然有效。

之后任何一方真正发送一条新文字或图片时，该会话重新出现在本人的列表。重试已送达消息的旧nonce只返回原编号，不会恢复会话项。清除同时删除本人尚未确认的、来自对方的图片下载授权（`media_grants8`，迁移前的旧授权除外），尚未下载的图片之后显示“图片已不在本机”；不再被引用的图片由服务器按“聊天图片与表情收藏”的规则清理。对方的授权和本机记录不受影响。

能力值7或15的主客户端可发送类型64：非零uint32请求号和peer账号ID字符串（最多64字节）。服务端只使用已认证账号作为owner，事务内复核双方账号和当前好友关系，按每连接好友操作额度限速。成功先发送类型65（peer字符串和uint64 clear_through），再发送类型19操作10结果0；失败仅返回对应操作结果。类型65同步当前主连接的清除水位，关闭对应私聊订阅、清理对应图片映射；其他会话和游戏端连接不受影响。新连接按每批最多50条同步持久水位，再加载好友/临时列表。客户端按水位过滤正在传输的旧分页、实时消息和图片映射；相同水位同步可以重复出现。

旧能力0、1、3不会接收新类型65。同账号现在只允许一个主连接，新登录不会挤掉原连接。清除仅刷新本人的联系人缓存，不广播到对方，不令全服务重查好友表。清除事件缓存有上限；重新登录时从数据库恢复持久水位。

`private_conversation_clears8` 由 `temporary_chat_clear.sql` 创建，`local_history_migration.sql` 在缺少时也会按相同定义补建；两个脚本都可重复执行并保留已有水位。服务账号需要该表的SELECT、INSERT、UPDATE权限，以及 `LOCAL_HISTORY_MIGRATION.md` 列出的会话索引和消息表DELETE权限。已有清除数据的部署不要移除该表，否则旧记录导出无法跳过已清除的部分。表结构与权限应先在备份后核对，程序不会自行执行DDL。

### 消息撤回

主客户端可以随时撤回自己发送的大厅或私聊消息，不限制消息年龄。已经下载到对方电脑的
图片文件无法从对方本地强制删除。撤回尚未送达的私聊图片时，服务器同时删除图片关联和对方的
下载授权；同一发送者还有另一条引用同一张图片、仍需要该授权的消息（未送达，或已送达但对方
尚未确认下载图片）时保留授权（`media_grants8.refs` 记录消息数，撤回一条减一，减到0才删除）；撤回大厅图片时，
没有其他大厅消息引用的图片立即从内存删除。大厅消息仍是服务器运行期间最近100条的内存缓存，服务器
重启后超出缓存的大厅消息只能由客户端本地缓存显示，不能再通过服务器撤回。

私聊撤回：消息尚未送达时，服务器把待送达消息标记为已撤回（正文替换为占位），送达时只带
撤回标记。无论是否已经送达，服务器都为对方保存一条持久撤回事件（`private_recalls8`），
对方在线时立即推送，离线时在下次登录后推送；对方客户端处理后确认，服务器再删除该事件。
已送达的消息已从服务器删除，服务器无法再核对它的发送者，所以对方客户端只在本机该编号
消息的发送者等于撤回者时才执行撤回。撤回者本机的记录在收到成功结果后由客户端更新；
重复撤回同一条消息（例如上次结果因断线丢失）同样返回成功，已排队的事件不重复保存。
撤回请求无论成功或被拒绝，每个连接每秒最多处理一次。
旧记录尚未被双方导出时，服务器同样把它标记为已撤回，之后导出得到的是撤回占位。

部署新服务器前，先备份并在账号数据库手动执行包内 `recall_schema.sql` 一次，步骤见
`RECALL_MIGRATION.md`，然后执行 `local_history_migration.sql`。`recall_schema.sql` 会幂等增加
`private_messages8.recalled_at`，执行迁移的账号需要ALTER权限；服务器运行账号需要该表的
SELECT、INSERT、UPDATE、DELETE权限和撤回事件表的SELECT、INSERT、DELETE权限。程序不会自动
执行迁移。

## 头像

主客户端可选择静态 JPG/PNG，裁剪为256×256后上传，界面以圆形显示。服务器重新解码并生成无原图元数据的PNG，再计算SHA-256；每张最多384 KiB，只允许更新当前认证账号自己的头像。头像持久保存到独立的 `user_avatars8` 表，重启后保留。

部署时在账号数据库执行包内 `avatar_schema.sql`，步骤见 `AVATAR_MIGRATION.md`。缺表只使头像功能不可用，登录、大厅、好友和私聊仍正常使用；程序不会自动执行SQL。头像为公开展示内容，已登录并加入头像功能的主客户端可按标识下载。好友仅同步已同意关系；大厅头像包以消息序号关联头像，增强聊天消息另提供作者账号ID。

类型25加入头像功能，26自己的标识，27/28/29开始上传、顺序分块、提交，30最终结果，31按标识下载，32/33/34下载开始、数据、结束，35好友头像标识，36大厅消息头像标识，37允许上传分块。上传须等待37，单次限时30秒；开始上传至少间隔10秒。下载按连接限速，每轮至多16个数据帧，不影响心跳和消息处理。旧主端未加入不会收到新头像包，游戏端不能使用头像协议。

## 聊天图片与表情收藏

主客户端可在大厅和私聊发送JPG、PNG、GIF图片，支持拖入、粘贴和截图；GIF保留动画。静态图片像QQ一样保留原始分辨率：JPG/PNG源文件最多32 MiB、每边最多65535像素、总像素最多64 MP（67,108,864像素，更大的源图片被拒绝），只有最长边超过8192像素或超过16,777,216像素（16 MP）时才等比缩小到同时满足两项（例如5000万像素照片、12000×3000全景图），规范PNG超过15 MiB时再按最长边85%逐步缩小；GIF规则不变（原文件最多2 MiB、最长边1024、最多120帧）。传输和最终保存的图片每张最多15 MiB（15728640字节），服务器用同一套规范化代码再次验证：完整解码后，已是规范PNG布局的文件按字节保存，所以32位客户端规范化后的内容和hash在64位服务器上保持不变（两者的WIC对相同像素压缩出的字节不同），其他内容由服务器重新编码。旧客户端看到“[图片]”，未启用媒体功能不会收到新包。私聊图片的hash随待送达消息（类型108）和旧记录导出（类型114）一起发送，不再需要类型52关联。

私聊图片（好友和临时会话）采用存储转发，服务器只保存到接收方取得为止：

- 上传提交（类型43）只做规范化并把结果暂存在本连接内存中最多120秒，结果码0带hash，不写数据库。紧接着的请求决定图片去向：发到大厅（49）放进大厅内存；发到私聊（51）时写入 `media_assets8` 和本人的上传记录 `media_uploads8`，再写消息；收藏（57）时随收藏写入。开始新的上传或120秒过期后暂存内容丢弃。因此额度不足（8）和数据库尚未完成图片升级（9）现在出现在发送或收藏的类型44结果中，不再出现在上传提交的结果中。
- 发送方客户端在上传前已把原图保存在本机，服务器不再为发送方写下载授权；只为接收方写一条待下载授权（`media_grants8`，记录发送方）。接收方在线时立即收到108和117，离线时在下次登录后收到；客户端在后台下载、写入本机后发送118，服务器删除该授权。送达确认109只删除消息，不等图片下载。
- 图片在以下条件都满足时由服务器后台自动删除：没有待下载授权，没有未送达的私聊消息或尚未被双方导出的旧记录引用，没有收藏，没有1小时内的上传记录（宽限期），大厅最近100条消息没有引用，也没有连接正在从数据库下载它。每次删除引用后立即检查相关图片；服务器启动15秒后及之后每10分钟再扫描一遍全部图片。迁移后的第一天（`media_collection8.enabled_after` 之前）不删除任何图片。详细规则、清理开关和长期不登录账号的手动清理见 `PRIVATE_MEDIA_MIGRATION.md`。
- 接收方确认后，图片最早在上传1小时后删除；已下载到本机的副本不受影响，换电脑或清空缓存后不能再从服务器下载，客户端显示“图片已不在本机”。

收藏随账号存入服务器，最多100项，重新登录和服务器重启后保留；收藏引用的图片不会被清理。下载、收藏、转发均检查当前认证账号的上传记录、收藏、私聊图片待下载授权、旧记录中的消息或大厅最近100条消息，不能仅凭hash读取自己未参与的私聊图片。收藏只存在于大厅内存中的图片、或随收藏一起提交刚上传的本机副本时，服务器把内容写入 `media_assets8`（不计入上传额度）；图片已不在服务器且没有提供内容时收藏返回5。在私聊中发送收藏的表情会复用已保存的图片，接收方同样下载并确认，图片因收藏继续保留。临时私聊允许发送图片，删除好友不影响已收到的图片，取消收藏只删除本人的收藏关联。

每账号最多1000张、合计256 MiB的上传额度只计算仍被保留的私聊图片（等待对方下载或已收藏），图片被清理后额度随之释放；大厅图片不计入额度。

部署时在账号数据库执行包内 `media_schema.sql`，详见 `MEDIA_MIGRATION.md`；图片授权表 `media_grants8` 由 `local_history_migration.sql` 创建，再执行 `private_media_migration.sql`（增加发送方、推送游标和消息数、创建清理开关表 `media_collection8`，可重复执行，步骤和运行账号新增的DELETE权限见 `PRIVATE_MEDIA_MIGRATION.md`），并把 `appdata.version` 改为 `26.9.29.1`。新表缺失只影响图片功能；服务器不自动迁移数据库。新协议类型38至57用于图片分块传输、消息图片关联和收藏列表，始终复用所属连接线程收发TLS。

原图升级：已有数据库须执行一次 `media_original_migration.sql`（把 `media_asset_size` 检查约束放宽到15 MiB，可重复执行），MySQL `max_allowed_packet` 至少16M（建议保持8.0默认的64M），新服务器和新主客户端一起部署，并把 `appdata.version` 改为新客户端版本：旧客户端遇到超过2 MiB的图片会判定为协议错误而断线。未执行迁移时，发送或收藏超过2 MiB的新图片时返回类型44结果码9（服务器尚未完成图片升级；上传提交本身不写数据库），控制台每30秒最多提示一次“图片升级未完成：……请执行media_original_migration.sql……MySQL错误码：3819”；max_allowed_packet过小时也返回9并提示调整。每连接同时最多一个上传和一个下载；进程内最多16个上传、16个下载、2个图片规范化（已传完的上传最多等待10秒取得名额），上传缓冲和下载缓冲分开计算，各自最多128 MiB（各约8张15 MiB图片），缓慢或停滞的上传不会影响下载，超出返回忙（3）。上传时限为60秒加每64 KiB 1秒（15 MiB为300秒，约0.45 Mbit/s仍可完成），超过30秒没有新数据的上传即作废（结果码1）并释放缓冲；下载也以60秒加每64 KiB 1秒为时限，超时后服务器停止发送并返回忙（3），客户端稍后重试。下载每轮最多1 MiB或20毫秒，本机15 MiB约0.3秒。新客户端在同一连接上一次只传一张图片（上传不与下载同时进行），双方都是先写一批帧再读一帧，两个方向同时大块传输会互相阻塞写入直至断线。读写整张图片的数据库操作每步等待5秒，其他图片请求仍为1秒。

图片暂存转入私聊或收藏操作时，上传额度随图片保留到操作及结果发送结束；缓冲先销毁，再归还额度。成功发布到大厅后改由大厅内存额度管理。图片规范化失败、下载校验失败及连接退出也按实际缓冲生命周期释放额度，暂存和下载按缓冲分配容量计费。

## 英雄排行榜

已认证的当前主客户端按需请求竞技场或大乱斗英雄排行榜，无需加入社交功能。登录不自动推送榜单，社交能力仍为15，旧客户端继续使用原功能；游戏端发送排行榜请求按协议错误断开。

服务端只读已有的herouse表，需要该表的SELECT权限，不写入统计、不自动建表或执行迁移。读取字段为ID、heroID、heroName、jjcNum、dldNum、jjcWin、jjcLos、dldWin、dldLos，其中ID用于稳定读取顺序；heroID每个英雄仅一行，计数沿用非负INT范围。NULL或负计数按0，NULL或负heroID跳过，heroID为0有效。名称为空白、无效UTF-8或超出960字节时显示“英雄 #编号”。最多读取4096条原始记录；超过上限、有效heroID重复、字段越界、表缺失或权限错误只使排行榜返回暂不可用，不发布部分数据，不影响登录、大厅、好友和私聊。

所有连接共享30秒只读缓存和同一份统计快照，每次成功加载标记服务端Unix秒更新时间。加载失败后退避5秒再试；旧快照仅供已经开始的完整回复继续使用，新请求返回暂不可用，不把旧榜单作为新结果发送。模式、排序、搜索和分页都在内存完成，每个连接请求间隔至少350毫秒，内容无效的尝试同样消耗额度。诊断使用中文且限流，不打印账号或SQL原文。

使用次数按次数降序、英雄编号升序排列。胜率为胜场除以胜场加败场，用整数交叉乘精确比较；有胜负记录的英雄排在无记录英雄之前，相同胜率再按使用次数降序、编号升序排列。竞技场与大乱斗使用各自统计。名次为完整榜单中的顺序名次，搜索后保持原名次；搜索英雄名UTF-8子串时仅ASCII字母不区分大小写，纯ASCII数字按英雄编号精确匹配，允许前导零。查询去除两端普通ASCII空格，最多32个Unicode字符及96字节；空查询显示全部。

类型66请求依次为非零uint32请求号、uint32模式（1竞技场、2大乱斗）、uint32排序（1使用次数、2胜率）、uint32页码（从0开始，最大409）和查询字符串。每页固定10条，超出过滤结果末页的有效页码收敛到末页，空榜单为第0页。

成功依次回复类型67、最多10条类型68和类型69。67依次为请求号、模式、排序、实际页码、页大小10、全榜数量、匹配数量、本页条数八个uint32，随后uint64更新时间和规范化查询字符串；68为请求号、全榜名次、英雄编号三个uint32，英雄名字符串，以及使用次数、胜场、败场三个uint64；69仅含请求号。失败仅回复70：请求号和结果两个uint32，结果1内容无效、2过于频繁、3暂不可用；成功不用结果包。每一页来自同一份不可变快照，客户端收到结束包后才发布完整页。包结构损坏或请求号为0使用协议错误101。

权限排行榜使用模式3，每种排序各显示前100名：排序1按权限数量降序、同数量按账号ID升序；排序2按账号ID升序。服务端仍读取并验证最多4096条候选，候选超过100条不会因此返回不可用；完成对应排序后只保留其前100名，再进行榜内昵称/公开ID搜索和分页。`total`是该排序实际榜单人数，最多100；每页10条，请求页码0～9，过滤后保留原榜单名次。原权限条目载荷和隐私规则不变，英雄模式1/2仍保持4096条上限与页码0～409。

## 累计在线时长与在线时间排行榜

`user8.onlineSeconds` 为 `BIGINT UNSIGNED NOT NULL DEFAULT 0`，单位保持为秒。部署方已添加此列，无需重复执行 ALTER TABLE；服务账号需要该列的 SELECT 和 UPDATE 权限。程序不自动执行数据库迁移，已有账号从当前保存值继续累计，默认0不补造历史时长。

只有认证并进入会话的主客户端计时，保持连接的挂机时间也计算；游戏端、登录失败、被拒绝的重复主登录和迟到的旧连接退出不重复计时。服务器使用单调时钟，每60秒由独立工作线程保存累计值；正常退出、连接断开、45秒无消息超时、改密码撤销会话和正常停机均触发剩余时长结算。按整秒累计，离线账本最终保存并清理时不足一秒的尾数舍去。断网的终点是服务器确认断开/超时的时刻，因此可能包含超时检测的等待时间。

保存采用固定基数加累计在线秒数的检查点，数据库只增不减，写入回执丢失后重试不会重复累加。数据库暂不可用时，在线和已离线账号的待保存时长保留在进程内，每5秒重试，重连不计入离线间隔；正常停机等待客户端工作线程结束后再做最后一次保存。数据库持续故障或强制结束进程时，内存中的未保存部分仍可能丢失，控制台会报告故障。此方案面向当前单服务进程：不要让多个服务实例同时为同一账号累计，也不要在服务运行期间手动重置该列。

在线榜只读已经保存的秒数，取大于0的前100名；按秒数降序、账号ID的二进制顺序升序打破同分。每页10条，搜索仅限榜内昵称和公开账号ID；隐藏ID不能按ID搜索，回包中ID为空字符串。昵称、头像和隐藏设置沿用账号资料；偏好读取失败时隐藏ID，头像不可用时使用默认头像。榜单共享30秒快照，结合60秒保存间隔，正常情况下新时长约在60～90秒内反映；不会把内存时长再次叠加到数据库值。

主客户端首页通过本人资料同步显示同一字段的累计在线时长，不受前100名或隐藏ID影响。类型58 `account_join` 接受空载荷、`uint32 features=1`（偏好）或 `features=3`（偏好加累计在线时长）；2及未知能力组合无效。仅向请求3的当前认证主客户端，在类型59原有账号ID、昵称、到期时间三个字符串及 `uint32 preferencesReady`、`uint32 hideId` 后追加 `uint32 onlineTimeReady`（0/1）和 `uint64 onlineSeconds`。读取失败时追加0和0，客户端显示暂不可用；读取成功的0秒是有效结果。旧客户端的空/1请求仍收到原有布局。

本人在线时长首次加入时读取，随后按连接每60秒最多读取一次并推送；手动刷新、修改昵称或隐私设置复用缓存，不增加数据库查询。查询仅使用当前认证账号，已落库值与排行榜一致，首页和榜单因刷新时刻不同可能短暂不同步。此扩展应先部署服务器，再发布新LA客户端；旧服务器只接受空/1请求，无法处理新客户端的3请求。登录校验和到期校验保持原协议，不需要数据库迁移。

好友头像提示使用社交能力1023（完整511再加位512“好友累计在线时长”）；类型14的格式和511相同，通知游标可选。只有协商此能力的客户端，类型17好友条目在原有最后离线时间后再追加 `uint32 onlineTimeReady`（0/1）及 `uint64 onlineSeconds`。仅已接受好友可返回可用时长；待处理申请、临时联系人、缺失或无效账号固定返回0和0，已接受好友的真实0秒返回1和0。服务端按当前认证账号批量查询已接受好友的 `user8.onlineSeconds`，每60秒刷新，关系重新同步时立即更新；读取失败清空缓存并显示暂不可用，不阻断好友或聊天。旧能力511等保持原回包布局，512只能随完整511共同启用；先升级服务器，再使用请求1023的新客户端。

客户端使用现有类型66～70，新增模式4，排序固定1，页码0～9，查询规则与现有榜单一致。类型67/69/70结构不变；**模式4的类型68**依次为 `uint32 requestId`、`uint32 rank`、账号ID字符串（最大64字节，可为空）、昵称字符串（最大512字节）、头像哈希字符串（空或64字节）、`uint32 hideId`（0/1）、`uint64 onlineSeconds`。不要用英雄榜或权限榜的条目结构解析模式4。旧客户端没有请求模式4时，不会收到这种新条目。

客户端显示按每360天=1年换算，采用“1年0天0小时0分”，不显示秒，不足一年时省略“年”：对原始 `onlineSeconds` 使用整数除法，年数=`s/31104000`，天数=`(s%31104000)/86400`，小时=`(s%86400)/3600`，分钟=`(s%3600)/60`。例如31104000秒显示为“1年0天0小时0分”，445500秒仍显示为“5天3小时45分”；小于一分钟显示为“0天0小时0分”。数据库及协议继续保存uint64秒数，不要把整数秒先转换成32位数或浮点数，支持JavaScript的客户端应使用BigInt解码uint64。排行榜比较始终使用原始秒数，因此显示到分钟相同的用户仍可能有不同名次。本工程只包含服务端，客户端需同步增加模式4入口、条目解析和上述显示。

可重复验证：`tests/run_account_online_time_tests.ps1` 使用模拟数据库读取和TLS发送，检查本人资料新旧回包、60秒缓存、读取失败恢复、好友新旧回包、社交能力协商、好友关系可见性和uint64精度；`tests/run_online_time_tests.ps1` 检查计时及会话生命周期，`tests/run_online_ranking_tests.ps1` 检查排序、隐私和实际回包格式，`tests/run_online_time_database_tests.ps1` 自建独立临时MySQL实例检查两种存储引擎和uint64精度。数据库测试仅连接自身临时实例，结束后停止该子进程并保留测试文件，不读取正式库。

## 协议与维护

两端 `network/protocol.h`、`network/tls_transport.h` 内容必须一致。TLS 内每帧固定 1024 字节，8 字节头部为大端有效长度和消息类型；字符串使用 2 字节大端长度加 UTF-8 内容。类型 1 登录、2 在线人数、3 账号资料、4 错误、5 心跳、6 心跳响应、7 游戏状态、8 加入大厅、9 发送聊天、10 聊天消息、11 历史开始、12 历史结束、13 发送结果。用户名、密码等字段有严格字节上限，非法长度和 UTF-8 会被拒绝。

聊天类型8和12为空载荷。类型9为非零uint32请求ID和正文字符串。类型10为uint64消息序号、uint32 UTC Unix秒时间、uint32本人标记（按认证账号精确比较，仅0/1）、昵称字符串（最多512字节）、正文字符串；增强尾字段与隐藏规则见“大厅账号ID显示与好友备注”。作者来自认证账号，客户端正文不能指定作者身份。未启用时包格式保持原样。类型11为uint32历史条数（最多100），表示替换本地旧历史，后续依次收到对应条数的类型10和类型12；期间可能收到心跳、人数、游戏状态、可见性更新或发送结果。类型13为uint32请求ID和uint32结果：0已接受、1正文无效、2发送过快。发送者同样接收服务器广播，以服务器消息序号为准。

当前登录格式必须两端同步更新：主客户端类型1依次发送 accountID、password、machineCode、key 四个字符串，再追加客户端类型和软件版本；游戏端类型2只提交 accountID 和客户端类型，不发送密码、机器码或 key。服务端要求游戏端的 accountID 与来源 IP 同时匹配已认证主客户端，否则返回错误103。主端成功回复含 accountName、ExpirationTime 和校验串；游戏端成功回复为空资料字段，随后接收首个人数。

增强聊天消息仍使用固定1024字节帧。正文、作者账号ID始终完整；当昵称加正文和账号ID超过一帧空间时，只按完整UTF-8字符边界缩短展示昵称。普通长度昵称和旧客户端格式不受影响。

类型 4 错误的载荷为一个大端 uint32：

- `1`：账号错误（账号不存在）；客户端显示“账号或密码错误”。
- `2`：密码错误；客户端显示“账号或密码错误”。
- `3`：机器码错误。
- `4`：茶会已过期。
- `5`：茶会已封禁（来自 special 中的权限 0）。
- `105`：最新版本配置不可用，主客户端拒绝登录。类型71是独立更新通知，载荷为最新版本字符串；不是凭据错误。
- `100`：数据库或服务器内部异常；`101`：格式/协议错误；`102`：尝试过于频繁；`103`：该账号已有主客户端在线（包括不同IP），或该账号同IP已有游戏端连接。拒绝新登录，保留原连接。
- `104`：该账号通过资料功能修改密码，当前会话已撤销，需要使用新密码重新登录。

成功校验串 LP2 实现在两端相同的 `network/login_proof.h`。LA 每次登录及重连均用系统安全随机数生成完整256位 nonce，key 是其64字符小写十六进制表示。服务端完成账号认证后，将固定域 `CHH8/login-proof/v2` 与 key、账号、机器码、软件版本、昵称、到期时间依次组成 SHA-256 输入；每个字段均使用4字节大端字节长度前缀和原始字段字节，避免字段拼接歧义。返回串固定为 `LP2:` 加64字符小写十六进制摘要，共68字符，客户端按本次完整挑战和同一组字段验证。

LP2 依赖已固定服务器证书的 TLS；它是无密钥摘要，不是独立签名、MAC 或授权凭证。旧 proof 不再接受，LA 与聊天服务器必须同步升级；缺少或无效校验串会显示“登录返回数据校验失败”，不会进入主界面。secondary 游戏端的空 profile 三字段及后续首个人数响应、下载协议均不变。`verify_response` 名称保留，但签名已改为接收完整登录 `Context`；手动重新加壳时应重新导入当前 EXE/PDB 并刷新函数选择。

测试记录位于 `D:\x96dbg\chh8d-server-work\verification.md`，包含独立本地 MySQL、跨实现 TLS、协议分包与多客户端验证。全部账号均为合成数据。

## 常见启动问题

- 提示缺文件：重新解压完整运行包，不要单独搬 EXE。
- 退出码 `0xC0000135`（或 -1073741515）：Windows 加载 DLL 失败；检查文件是否齐全及目标系统兼容性。
- “无法打开证书文件”：证书缺失或运行账号无读取权限；证书应与 EXE 同目录。
- “端口监听失败，错误码：10048”：5555端口被其他进程占用；不要同时运行两份服务端。
- `10049`：指定的绑定地址不是本机地址；默认使用 0.0.0.0。
- 证书到期或尚未生效：检查目标机日期时间及证书有效期，不要绕过证书验证。

运行包为 x64；目标服务器 Windows 版本尚未提供，因此跨机器启动是否成功仍需以目标机实际输出确认。本地诊断文件只记录启动和错误，不记录账号密码；数据库登录记录按上节约定保存。若程序尚未进入入口（系统加载 DLL 失败），可能没有程序日志，此时查看启动脚本保留的提示。
